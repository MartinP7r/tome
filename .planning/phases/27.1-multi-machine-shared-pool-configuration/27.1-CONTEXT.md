# Phase 27.1 Context: Multi-Machine Shared Pool Configuration

## Why This Phase Exists

The current portable `tome.toml` owns every `[directories.*]` entry. That assumes all machines share one source and distribution topology. The intended model is instead one Git-backed pool of accumulated skills used by machines with different purposes, such as an agent-hosting Mac mini and a development MacBook.

Phase 28's original Configuration UI plans encoded the current boundary and were superseded before further implementation.

## Locked Decisions

### Configuration boundaries

- Shared pool policy remains in `<config-dir>/tome.toml`.
- Complete named machine profiles live in `<config-dir>/machines/<profile>.toml` and are committed with the Tome Git repository.
- A profile is a generic named configuration. Tome does not distinguish physical-machine names from reusable role names or enforce uniqueness.
- Local runtime settings live in `~/.config/tome/settings.toml`.
- Local settings select one profile and store runtime consent such as Git synchronization and managed-plugin installation policy.
- New configurations write TOML, not JSON.
- `directory_overrides` is deprecated rather than immediately removed. Existing entries continue to load with a deprecation warning, but new setup flows do not generate them.

### Shared pool semantics

- Skills discovered on any machine accumulate in the shared library.
- A source disappearing or being absent from the active profile does not remove its skill from the pool.
- Explicit pool removal also adds the skill to the shared `exclude` policy so another machine cannot silently re-import it.
- Restoring a removed skill requires an explicit action that clears the exclusion.
- Shared provenance preserves the stable source identity, source kind, version and commit SHA when available, original content hash, import timestamp, importing profile or machine identity, and the observed local path as non-authoritative metadata.
- Later observations extend provenance history rather than erasing the original import record.
- Same-name skills with different content stop reconciliation and require explicit resolution. Tome never resolves these conflicts by timestamp or silent source priority.

### Git synchronization

- Tome manages Git pull, commit, and push around `tome sync`, controlled by local `git_sync = "ask" | "always" | "never"` policy.
- `ask` presents two confirmations: pull before reconciliation, then commit and push after a successful reconciliation.
- The post-sync confirmation shows the exact pool change summary.
- Pull is fast-forward-only. Diverged history is reported for manual resolution.
- Publish refuses while the branch is behind or diverged.
- CLI flags can override the persisted Git policy for one invocation.
- `tome status` reports repository cleanliness, staged and unstaged counts, added/modified/deleted counts, upstream ahead/behind state, latest commit age, and other reliable local Git health data.
- Exact last-push time is not promised unless implementation research identifies a reliable source or Tome deliberately records it.

## Intended File Shape

```text
<TOME_HOME>/
  skills/
  .tome/
    tome.toml
    tome.lock
    .tome-manifest.json
    machines/
      mac-mini.toml
      macbook-air.toml

~/.config/tome/settings.toml
```

The actual config directory remains resolved through Tome's existing `resolve_config_dir` behavior; `.tome/` above illustrates the current repository layout.

## Planning Constraints

- Preserve CLI behavior outside the intentionally changed configuration, cleanup, conflict, and Git-consent contracts.
- Design migration from the current portable `[directories.*]` plus local `machine.toml` model before implementation.
- Reuse existing `exclude`, backup Git primitives, structured reports, progress events, and checked atomic TOML writes where they fit.
- Do not resume or reuse Phase 28's superseded plans. Re-plan Phase 28 only after this phase is complete and verified.

## Research Questions For Planning

- Exact schema split among pool policy, machine profiles, and local runtime settings.
- Manifest and lockfile evolution needed for provenance history and cross-profile ownership.
- Migration and deprecation warning behavior for current `machine.toml` and `directory_overrides`.
- Conflict artifact and resolution command design.
- Whether existing `backup` commands should be renamed or extended for pool synchronization.
- Reliable and portable Git status fields for CLI and desktop reports.
