## User Constraints (from CONTEXT.md)

### Locked Decisions
- Shared pool policy remains in `<config-dir>/tome.toml`.
- Complete named machine profiles live in `<config-dir>/machines/<profile>.toml` and are committed with the Tome Git repository.
- A profile is a generic named configuration. Tome does not distinguish physical-machine names from reusable role names or enforce uniqueness.
- Local runtime settings live in `~/.config/tome/settings.toml`.
- Local settings select one profile and store runtime consent such as Git synchronization and managed-plugin installation policy.
- New configurations write TOML, not JSON.
- `directory_overrides` is deprecated rather than immediately removed. Existing entries continue to load with a deprecation warning, but new setup flows do not generate them.
- The three persisted layers (pool policy, machine profile, local settings) each deserialize into separate structs and merge into the existing effective `Config`, so downstream sync/status code keeps operating on the current flat model.
- Existing path-normalization rules are preserved during migration; paths are not rewritten to new portable forms by migration itself.

- `tome.lock` becomes the tracked, authoritative provenance catalog for the shared pool. It carries cross-profile ownership and history that the Git repository reviews.
- Each source entry keeps its first and latest observation: original stable identity and import time plus current version, commit SHA, content hash, and last observed profile. Intermediate states live in Git history rather than the file.
- `.tome-manifest.json` remains a single local, derived, rebuildable operational index for the current checkout. It is never authoritative for ownership or removal and is not tracked as provenance.

- Skills discovered on any machine accumulate in the shared library.
- A source disappearing or being absent from the active profile does not remove its skill from the pool.
- Explicit pool removal also adds the skill to the shared `exclude` policy so another machine cannot silently re-import it.
- Restoring a removed skill requires an explicit action that clears the exclusion.
- Shared provenance preserves the stable source identity, source kind, version and commit SHA when available, original content hash, import timestamp, importing profile or machine identity, and the observed local path as non-authoritative metadata.
- Later observations extend provenance history rather than erasing the original import record.
- Same-name skills with different content stop reconciliation and require explicit resolution. Tome never resolves these conflicts by timestamp or silent source priority.
- A chosen conflict winner persists as a shared source pin in `tome.toml` pool policy, so every profile honors the same source for that skill.
- Unresolved conflicts are reported as structured output only. No conflict cache or tracked conflict records are written; the next sync reproduces the conflict from sources and resolution writes only the source pin.
- Once a source is pinned, that source may update the pool; later observations from the losing source are ignored with a warning rather than re-raising the conflict.
- If the pinned source disappears or is unavailable, the pool content and the pin are preserved with a warning. Tome never fails over to an alternate source automatically.

- Tome manages Git pull, commit, and push around `tome sync`, controlled by local `git_sync = "ask" | "always" | "never"` policy.
- `ask` presents two confirmations: pull before reconciliation, then commit and push after a successful reconciliation.
- The post-sync confirmation shows the exact pool change summary.
- Pull is fast-forward-only. Diverged history is reported for manual resolution.
- Publish refuses while the branch is behind or diverged.
- CLI flags can override the persisted Git policy for one invocation.
- `tome status` reports repository cleanliness, staged and unstaged counts, added/modified/deleted counts, upstream ahead/behind state, latest commit age, and other reliable local Git health data.
- Exact last-push time is not promised unless implementation research identifies a reliable source or Tome deliberately records it.
- The pull prompt may fast-forward the entire mixed repository (it also contains unrelated directories) only after explicit confirmation showing the remote summary. Publishing stays restricted to Tome-owned paths.
- If Tome creates the local pool commit but push fails, the commit is kept and the next sync offers to push all ahead commits. No rollback of the local commit.
- Post-sync commits include all Tome-owned changes present after the preview, including Tome-owned edits that pre-dated this sync (e.g. a manually edited machine profile), while unrelated paths remain excluded.
- Sync runs are serialized by a per-repository lock file containing the owner PID and timestamp. A concurrent `tome sync` fails fast with a clear message; the lock is released on exit. Stale-lock auto-cleanup is not implemented.

- Migration is interactive-only in this phase (single-user product). No automation or `--yes` path.
- `tome migrate profiles` requires a terminal, asks for the profile name explicitly, shows the full migration preview, and requires confirmation before writing.
- Original files are backed up as timestamped siblings beside each changed file (`tome.toml.pre-profiles-<timestamp>`, `machine.toml.pre-profiles-<timestamp>`), using collision-free timestamps.
- `directory_overrides` are baked into the new profile as effective directory paths; the original override syntax survives only in the backup.
- The active legacy `~/.config/tome/machine.toml` is removed only after all new files are safely written; its backup remains.
- Migration refuses an already-existing profile name and refuses malformed legacy input rather than salvaging fields.
- The preview shows both a field-mapping summary and the file diffs. Rollback is documented as manual restore from the backups; no immediate rollback command is offered.

## Summary

This phase is a contract replacement at the configuration and sync boundary, not a UI feature. Keep the existing `Config` as the downstream effective model: load pool policy, the explicitly selected profile, and local settings into new layer-specific structs; validate them; then project a fresh `Config` plus distribution preferences. The current code already separates `Config` loading from `MachinePrefs`, but it loads a missing machine file as defaults and applies overrides to a mutable config copy, so it cannot meet the required no-profile/no-side-effects behavior without a new top-level loader. [VERIFIED: crates/tome/src/config/mod.rs:42-64, 152-255] [VERIFIED: crates/tome/src/machine.rs:236-257]

The high-risk seams are discovery/consolidation, cleanup, lockfile generation, and Git. Today discovery silently keeps the first same-name candidate in directory-name order, consolidation may overwrite a manifest-owned library directory, and cleanup deletes a skill when its still-configured source no longer contains it. Those behaviors directly contradict the shared-pool conflict and accumulation contracts; introduce a pool reconciliation phase that collects and hashes all candidates before calling consolidation or cleanup. [VERIFIED: crates/tome/src/discover.rs:241-379] [VERIFIED: crates/tome/src/library.rs:244-375] [VERIFIED: crates/tome/src/cleanup.rs:313-491]

**Primary recommendation:** Create a `pool` domain module that owns layered-load projection, candidate reconciliation, catalog mutation, explicit removal/restore/conflict resolution, and Git coordination; retain `Config`, `MachinePrefs`-style filtering, consolidation, and distribution as consumers of its validated effective output.

### Pattern 1: Load, validate, then project
**What:** Separate persisted schemas from the existing operational `Config`; merge only after validating selected-profile existence and all three inputs.

**When to use:** Every CLI command and every desktop command that would otherwise call `Config::load_or_default`.

**Implementation direction:** Make a single `load_effective_context(...) -> Result<EffectiveContext>` public domain entry point. It must read local settings first, reject absent/empty/invalid/missing profile before resolving sources or creating `TomePaths`, then load pool TOML and profile TOML, preserve existing tilde expansion and `Config::validate`, and return both the effective config and local runtime policy. The current `Config::load_with_overrides` order is the reusable model for validate-after-projection, but `directory_overrides` must only be accepted as legacy input and emit a deprecation warning. [VERIFIED: crates/tome/src/config/mod.rs:152-234] [VERIFIED: crates/tome/src/config/overrides.rs:22-97]

### Pattern 2: Plan/reconcile/commit mutation barrier
**What:** Discover every candidate and hash it before modifying library, manifest, catalog, exclusions, or distribution.

**When to use:** Sync, explicit pool removal/restore, and conflict resolution.

**Implementation direction:** Replace `discover_all`'s first-wins result with a candidate collection keyed by skill name, then classify candidates deterministically by stable source identity and content hash. Only a conflict-free reconciliation plan may call the existing copy/distribution functions. This prevents the current alphabetical first-wins branch and overwrite path from reaching disk. [VERIFIED: crates/tome/src/discover.rs:249-379] [VERIFIED: crates/tome/src/library.rs:244-375]

### Pattern 3: Write staged artifacts, commit the new layout last
**What:** For multi-file migration, write all new files and backups first, then remove legacy `machine.toml` only as the final operation.

**When to use:** `tome migrate profiles` only.

**Implementation direction:** Build a pure migration plan and rendered diff; after TTY confirmation, create timestamped sibling backups, atomically write pool policy/profile/settings, validate by reloading the projected effective context, then remove the legacy active machine file. Existing one-file temp-and-rename helpers preserve one target, but do not make a multi-file transaction; injected-failure tests must verify the legacy pair remains usable until the final deletion boundary. [VERIFIED: crates/tome/src/config/mod.rs:257-361] [VERIFIED: crates/tome/src/machine.rs:370-389]

### Pattern 4: Read-only Git preflight followed by bounded mutation
**What:** Parse one machine-readable repository snapshot; use it to block unsafe pull/publish before any Git mutation.

**When to use:** Git policy is `ask` or `always`, or an invocation override requests pull/publish.

**Implementation direction:** Use `git --no-optional-locks status --porcelain=v2 --branch --show-stash` for parsing tracked/untracked state and upstream ahead/behind headers. `git status` porcelain is documented as stable for scripts; v2 exposes branch and ahead/behind headers. The `--no-optional-locks` prefix matters because ordinary `git status` can refresh and write the index. [CITED: https://git-scm.com/docs/git-status]

For a safe pull, fetch first, determine the configured upstream, compare ancestry, and use `git merge --ff-only <upstream>` only after explicit policy consent. Git documents that `--ff-only` refuses a non-fast-forward merge. [CITED: https://git-scm.com/docs/git-merge]

For publish, reject any pre-existing staged or unmerged entries; enumerate changed owned paths; stage only those pathspecs with `git add -- <pathspec...>`; commit; then push. Do not run `git add -A`, `reset`, `restore`, or `checkout` in the shared-pool coordinator. Git’s documentation states that index-updating commands modify the index, which is why pre-existing staged state must block rather than be repaired by Tome. [CITED: https://git-scm.com/docs/git-update-index]

### Recommended persisted schema

Use separate `#[serde(deny_unknown_fields)]` structs with deterministic `BTreeMap` / `BTreeSet` fields. This matches current config parsing and deterministic catalog ordering. [VERIFIED: crates/tome/src/config/types.rs:414-443] [VERIFIED: crates/tome/src/lockfile.rs:21-28]

- **Pool policy (`tome.toml`):** `library_dir`, `exclude`, `backup`, and `source_pins` keyed by skill name. This is the only shared policy layer.
- **Machine profile (`machines/<profile>.toml`):** complete `directories`, global `disabled`, `disabled_directories`, and per-directory filters. It must contain no local consent.
- **Local settings (`settings.toml`):** selected `profile`, `git_sync`, managed-plugin consent, and backup runtime preference.
- **Catalog (`tome.lock`):** schema version plus skills keyed by name. Each entry must contain stable identity, initial observation, current observation, and an ordered/deduplicated observation list sufficient to retain first and latest facts. The observed local path belongs inside an observation and is not an authority for source identity.

Do not reuse `LockEntry.source_name: Option<DirectoryName>` as the source identity: it currently records only the current directory owner and the catalog generator replaces each entry from the manifest/current discovery. [VERIFIED: crates/tome/src/lockfile.rs:49-77, 134-179]

### Anti-Patterns to Avoid
- **Calling the old `Config::load_or_default_with_overrides` for normal commands:** a missing machine file defaults successfully, violating explicit profile selection. [VERIFIED: crates/tome/src/config/mod.rs:237-255] [VERIFIED: crates/tome/src/machine.rs:245-257]
- **Updating the catalog after consolidation:** a conflict must halt before any pool/manifest/catalog/distribution mutation.
- **Keeping the existing missing-source cleanup:** it deletes a configured-source skill in noninteractive mode. [VERIFIED: crates/tome/src/cleanup.rs:421-491]
- **Relying on `.gitignore` for safe publish:** it cannot prove the index was untouched; stage explicit owned paths only.
- **Making separate desktop load logic:** current desktop `load_context` bypasses machine preferences entirely, so replace it with the same Rust effective-context loader. [VERIFIED: crates/tome-desktop/src/commands.rs:63-79]

## Common Pitfalls

### Pitfall 1: Existing cleanup deletes a temporarily absent source
**What goes wrong:** A profile with a source that is empty/unavailable can cause its library entry to be deleted.

**Why it happens:** Current cleanup classifies a still-configured source with no discovered skill as Case 2 and auto-removes it outside an interactive prompt. [VERIFIED: crates/tome/src/cleanup.rs:313-491]

**How to avoid:** Remove source-absence deletion from shared-pool sync completely. Only an explicit pool-remove plan may delete library/catalog state and must add the shared exclusion first.

**Warning signs:** Any test asserting `!library/<skill>.exists()` after a source/profile disappearance is a legacy behavior test that must be replaced.

### Pitfall 2: Duplicate discovery already chooses a silent winner
**What goes wrong:** Different content with the same skill name is chosen by alphabetical directory order.

**Why it happens:** `discover_all` uses a `seen` map and retains the first candidate; the warning names the winner after the fact. [VERIFIED: crates/tome/src/discover.rs:249-379]

**How to avoid:** Return all candidates from collection, hash all of them, and perform deterministic identity/content classification before consolidation.

### Pitfall 3: Current lockfile is a regenerated snapshot, not history
**What goes wrong:** Calling current `lockfile::generate` after sync erases earlier source facts because it recreates entries from the local manifest and discovered skills. [VERIFIED: crates/tome/src/lockfile.rs:134-179]

**How to avoid:** Replace generation with catalog merge semantics: preserve first observation, update latest observation for same identity, append only a meaningfully new observation, and serialize deterministically.

### Pitfall 4: Current backup Git helpers stage the entire repository
**What goes wrong:** `git add -A` can stage unrelated dotfiles in a shared pool repository. [VERIFIED: crates/tome/src/backup.rs:66-87, 102-136]

**How to avoid:** Do not extend `backup::snapshot` for pool synchronization. Extract shared low-level command execution if useful, but implement `repo_sync` with index preflight and explicit deduplicated owned pathspecs.

### Pitfall 5: Status can mutate Git’s index
**What goes wrong:** A read-only status command may refresh/write index metadata.

**Why it happens:** Git documents that ordinary `git status` can refresh the index and recommends `git --no-optional-locks status` for background/script usage. [CITED: https://git-scm.com/docs/git-status]

**How to avoid:** Use `git --no-optional-locks status --porcelain=v2 --branch --show-stash`; make all status health collection one snapshot and never invoke staging/repair commands.

### Pitfall 6: Single-file atomic writes do not make migration atomic
**What goes wrong:** New policy/profile/settings files may be partly installed while legacy inputs are removed.

**How to avoid:** Stage all writes, reload/validate the new effective context, and delete the legacy machine file last. Add deterministic injected-failure seams to every boundary.

## Open Questions

1. **Exact authoritative catalog wire format and schema-version migration path**
   - What we know: the current `tome.lock` is versioned JSON and current config persistence is TOML; locked context requires new configurations to write TOML and makes the lock catalog authoritative. [VERIFIED: crates/tome/src/lockfile.rs:21-28, 283-315]
   - What's unclear: whether “new configurations write TOML” includes the lock catalog or only the three configuration layers.
   - Recommendation: plan an initial schema task that defines an explicit catalog version and supports a one-time legacy read; do not silently change format without tests and a migration preview.

2. **Pool-owned path roots when `library_dir` is outside `tome_home`**
   - What we know: `library_dir` is configurable and may be separate from `tome_home`; config files live under `config_dir`. [VERIFIED: crates/tome/src/paths.rs:72-153]
   - What's unclear: whether the external library must be inside the shared Git repository before Git synchronization is enabled.
   - Recommendation: require all publishable owned paths to be descendants of the repository worktree; otherwise report Git synchronization unavailable while retaining local-only sync.

3. **Repository lock placement**
   - What we know: concurrent CLI/desktop sync already has only in-process desktop mutex protection. [VERIFIED: crates/tome-desktop/src/sync_state.rs:1-28]
   - What's unclear: exact lock filename/location must avoid both tracked pool files and Git index behavior.
   - Recommendation: use one untracked lock file under the resolved config directory, created with create-new semantics and holding PID/timestamp; never auto-delete a stale lock.
