# Phase 27.1: Multi-Machine Shared Pool Configuration — Specification

**Created:** 2026-08-18
**Ambiguity score:** 0.10 (gate: <= 0.20)
**Requirements:** 8 locked

## Goal

One Git-backed Tome pool accumulates skills and provenance from independently configured machine profiles, distributes the pool according to the active profile, and synchronizes only Tome-owned repository content under explicit machine-local consent without silent deletion, overwrite, or Git-index mutation.

## Background

Today `tome.toml` owns `library_dir`, exclusions, backup policy, and every `[directories.*]` entry. `~/.config/tome/machine.toml` combines local disables, per-directory filters, path overrides, and managed-plugin consent. This assumes machines share one directory topology even when a Mac mini running agents and a development MacBook need different sources and targets.

Manifest ownership is singular and later observations replace prior source metadata. Duplicate names use first-directory-wins behavior, and missing configured source content can be removed automatically. Git integration pulls before sync without consent, offers a broad `git add -A` commit afterward, and can include unrelated content because `TOME_HOME` may be a larger dotfiles repository. Status does not expose Git health.

This phase changes those contracts before Phase 28 builds configuration UI against them.

## Requirements

1. **POOL-01 — Layered configuration and explicit profile selection**: Tome loads shared pool policy, one named machine profile, and local runtime settings into one validated effective configuration.
   - Current: Shared `tome.toml` contains all directory topology; local `machine.toml` contains a mixture of preferences, overrides, and consent. Named profiles and `settings.toml` do not exist.
   - Target: Pool-wide `library_dir` and `exclude` policy remain in `<config-dir>/tome.toml`. Complete directory topology, globally disabled skills/directories, and per-directory allow/block lists live in `<config-dir>/machines/<profile>.toml`. `~/.config/tome/settings.toml` selects the active profile and stores runtime policy and consent, including `git_sync`, managed-plugin installation, and backup behavior. Profile names use Tome's validated identifier rules. Missing settings, no selected profile, an invalid name, or a missing profile stops before side effects, lists available profiles, and directs the user to `tome profile select <name>` or `tome init`. Tome never guesses a profile, including when only one exists.
   - Acceptance: CLI and desktop load the same effective configuration for a valid profile; fixtures for missing settings, empty selection, invalid identifier, and nonexistent profile all fail before filesystem mutation with available-profile and recovery guidance; loading the same three files repeatedly produces the same effective configuration.

2. **POOL-02 — Explicit, previewed, atomic migration**: Existing `tome.toml` plus `machine.toml` installations migrate only through `tome migrate profiles`.
   - Current: No migration exists for the current topology; `directory_overrides` is active and documented as a normal configuration layer.
   - Target: Normal commands detect the legacy layout and refuse it with migration instructions. Migration asks for a profile name, previews every field destination, backs up all inputs, and atomically writes pool policy, the named profile, and local settings. Failure or interruption leaves the original files usable. Re-running migration after success is a no-op. Existing `directory_overrides` continue to load with a deprecation warning, are preserved during migration, and are not generated by new setup flows.
   - Acceptance: Migration fixtures prove every current field lands exactly once in the intended layer, empty collections and configured order are preserved deterministically, backups exist before replacement, injected failures at each write boundary leave the old layout intact, and a second invocation changes no bytes.

3. **POOL-03 — Accumulating pool and explicit removal**: Discovery adds or updates pool content but source absence never deletes accumulated skills.
   - Current: Missing content from a configured source can be removed automatically; a profile with no discovered skills exits before distributing existing pool content; `tome remove skill` does not create a shared exclusion.
   - Target: A source missing from the active profile, temporarily unavailable, empty, or no longer containing a skill leaves pool content intact. Existing pool skills still distribute when the active profile has no discovery sources. Explicit pool removal deletes the skill and adds its name to shared `exclude`, preventing all profiles from re-importing it. Explicit restore clears the exclusion before import. Repeated sync or removal is idempotent.
   - Acceptance: Two-profile tests import on profile A, sync and distribute on target-only profile B, then remove or hide A's source without deleting pool content; explicit removal deletes content and writes `exclude`; subsequent discovery cannot re-import until restore clears it; cancellation never produces a partially deleted pool entry.

4. **POOL-04 — Shared provenance and stable source identity**: Every pool skill retains version-controlled origin history across profiles and updates.
   - Current: Manifest and lockfile retain one current owner/path and limited provenance; consolidation replaces entries, while the richer manifest is currently ignored by Git.
   - Target: Shared tracked metadata preserves stable source identity, source kind, normalized locator when available, version and commit SHA when available, content hash, observation time, observing profile, and local observed path as non-authoritative information. Registry ID identifies managed sources; normalized Git URL identifies Git sources across profiles; `<profile>/<directory-name>` identifies ordinary local directories. Same-identity updates replace pool content while retaining earlier observations. Duplicate identical observations are deduplicated, not appended indefinitely.
   - Acceptance: Round-trip and cross-profile tests preserve the original source locator and commit SHA after later updates; equal registry IDs and normalized Git URLs merge across profile names; ordinary local sources remain distinct across profiles; repeated identical syncs produce byte-identical provenance; concurrent or interrupted writes preserve a valid prior artifact.

5. **POOL-05 — Explicit content conflict handling**: Independent sources with the same skill name and different content cannot silently choose a winner.
   - Current: Discovery sorts directories and retains the first duplicate name with a warning, without comparing content equality or preserving both candidates.
   - Target: Same-name/same-content observations merge as provenance. A same-name/different-content observation from a different stable source produces a structured conflict containing every candidate source, hash, and location; reconciliation halts before pool, manifest, lockfile, exclusion, or distribution mutation. Resolution supports retaining the current pool candidate, accepting one named source candidate, or globally excluding the skill. Repeating an unresolved conflict remains read-only and deterministic.
   - Acceptance: Equality, two-way difference, and three-candidate tests prove identical content merges, differing content exits nonzero with stable candidate ordering, no pool bytes or metadata change, and each minimum resolution action yields the selected deterministic result on the next sync.

6. **POOL-06 — Consent-driven Git synchronization**: Pull and publish around sync obey machine-local `git_sync = "ask" | "always" | "never"` policy and one-run CLI overrides.
   - Current: A configured remote pulls automatically; an interactive CLI may offer a commit; push follows that commit automatically; desktop behavior differs; configuration is loaded before pull.
   - Target: `ask` prompts separately before pull and before post-sync commit/push; `always` performs both when safe; `never` performs neither. In noninteractive mode, `ask` runs local-only and warns that automation should select `always`. Pull is fast-forward-only and occurs before loading shared pool policy/profile for reconciliation. Publish refuses when behind, diverged, conflicted, merging, or rebasing. The publish prompt shows the exact Tome-owned change summary. A no-change sync creates no commit. The user can decline Git handling and continue local-only.
   - Acceptance: Policy/TTY matrix tests cover all three values and one-run overrides; pulled profile changes affect the same invocation; divergence and operation-in-progress states produce no merge or commit; two unchanged syncs create no additional commit; CLI and desktop return equivalent structured Git outcomes.

7. **POOL-07 — Surgical staging without index mutation**: Tome commits only its owned pool paths and never rewrites the user's existing Git index.
   - Current: Snapshot and sync commit paths use repository-root `git add -A`, which can stage unrelated files in a broader dotfiles repository.
   - Target: Any pre-existing staged entry or unresolved conflict blocks Tome-managed pull/publish with cleanup guidance. Unstaged changes outside Tome-owned paths are reported and left untouched. Dirty Tome-owned paths block pull until cleaned or published, but the user may continue local-only. Publish stages explicit changed pathspecs only: the configured library, pool policy, lockfile, tracked provenance, machine profiles, and shared exclusions. Source caches such as `repos/` are never staged. Tome never un-stages, restores, or otherwise alters unrelated index/worktree entries.
   - Acceptance: A repository fixture containing dirty `agent-notes/`, staged unrelated content, changed pool files, untracked cache files, and overlapping Tome pathspecs proves staged state blocks managed Git operations; after cleanup, only deduplicated Tome-owned paths enter the commit; unrelated unstaged/untracked bytes and index state remain unchanged.

8. **POOL-08 — Profile and Git health reporting**: Status exposes the active profile and reliable structured repository state.
   - Current: `StatusReport` has pool/config/lockfile/machine preference data but no active named profile or Git health.
   - Target: Text, JSON, and desktop status report active profile, clean/dirty state, staged and unstaged totals, added/modified/deleted counts, upstream ahead/behind counts, divergence, latest commit age, remote/upstream availability, and operation-in-progress state. Clean repositories report zero counts. Missing Git, repository, remote, upstream, or timestamps are explicit unavailable states rather than fabricated values. Status is read-only and internally consistent from one repository snapshot.
   - Acceptance: Fixtures for clean, staged, unstaged, mixed, ahead, behind, diverged, detached, no-remote, no-upstream, merge/rebase, and non-repository states produce matching structured and rendered values; repeated status calls do not alter repository bytes or index state.

## Boundaries

**In scope:**
- Shared pool policy, versioned named machine-profile, and local runtime-settings schemas and loaders.
- Profile list/select/create support needed for bootstrap and migration.
- Explicit current-layout migration and `directory_overrides` deprecation behavior.
- Accumulating cleanup/removal semantics and shared exclusion-based tombstones.
- Version-controlled provenance history and stable source identity.
- Structured conflict detection and minimum conflict-resolution actions.
- Git consent, safe pull/publish orchestration, surgical path staging, and structured outcomes.
- Profile and Git status in domain, CLI, JSON, and existing desktop status surfaces.
- CLI/desktop parity, atomic writes, bindings regeneration, and watcher coverage for the new artifacts.

**Out of scope:**
- Phase 28 configuration editor and first-run desktop UX — it must be re-planned after these contracts stabilize.
- Visual merge tooling for Git history conflicts — divergence remains a manual Git resolution.
- Skill-content merge or rename tooling — conflicts select an existing candidate or exclude the skill.
- Automatic profile selection by hostname or single-profile inference — selection is always explicit.
- Profile composition or inheritance — one selected profile is complete.
- A Tome-hosted synchronization service, accounts, telemetry, or non-Git transport.
- Exact last-push timestamp — ordinary local Git metadata does not reliably provide it.
- Removing `directory_overrides` parsing — this phase deprecates but preserves it.

## Constraints

- Unix-only filesystem and symlink model remains unchanged.
- The Git repository may contain unrelated dotfiles outside Tome ownership.
- No unrestricted `git add -A`, index reset, unstage, worktree restore, non-fast-forward merge, or automatic conflict resolution.
- All shared and local config writes remain checked and atomic.
- Shared metadata must survive concurrent CLI/desktop observation without corruption and remain suitable for Git review/merge.
- No JavaScript-side validation or side-effect policy; Rust remains authoritative.
- CLI and desktop consume the same effective configuration and structured domain results.
- `directory_overrides` remains readable with a warning for at least this phase.

## Acceptance Criteria

- [ ] Valid pool policy + selected profile + local settings load identically in CLI and desktop.
- [ ] Missing, empty, invalid, or nonexistent profile selection fails before side effects and never auto-selects a profile.
- [ ] `tome migrate profiles` previews, backs up, and atomically maps every legacy field exactly once; repeated migration is byte-idempotent.
- [ ] Deprecated `directory_overrides` load with a warning and new setup does not emit them.
- [ ] A skill imported on one profile remains available and distributable on a profile with no discovery sources.
- [ ] Missing/unavailable sources never delete pool content; explicit removal writes shared `exclude`, and restore clears it.
- [ ] Shared provenance preserves original locator/hash/version/SHA and deduplicates repeated identical observations.
- [ ] Managed registry IDs and normalized Git URLs unify sources across profiles; local sources use `<profile>/<directory-name>` identity.
- [ ] Same-name/same-content observations merge; independent differing content halts before any pool or distribution mutation.
- [ ] Conflict reports are deterministic and retaining, accepting, or excluding a candidate resolves the next sync predictably.
- [ ] `git_sync` ask/always/never and CLI overrides produce the specified pull/publish behavior in TTY and non-TTY runs.
- [ ] Pull occurs before shared configuration is loaded and remains fast-forward-only.
- [ ] Existing staged/conflicted/merge/rebase states block managed Git operations without altering index or worktree state.
- [ ] Unrelated unstaged and untracked files remain byte-identical and absent from Tome commits.
- [ ] Tome stages only changed library/config/profile/lock/provenance/exclusion pathspecs and never stages caches.
- [ ] A no-change sync produces no commit; declined or unsafe Git handling can continue local-only.
- [ ] Text, JSON, and desktop status agree across clean, dirty, ahead, behind, diverged, unavailable, and operation-in-progress fixtures.
- [ ] Repeated load, migration, sync, conflict detection, and status operations are idempotent for unchanged inputs.
- [ ] Injected interruption at every multi-file write boundary leaves the previous configuration, pool, and provenance readable.
- [ ] Tome never silently deletes accumulated skills, guesses an active profile, chooses an independent conflict winner, performs network Git work for noninteractive `ask`, or commits unrelated repository content.
